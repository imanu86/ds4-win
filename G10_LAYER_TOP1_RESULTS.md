# G10 native Windows layer-local resident expert cache

Date: 2026-07-13
Branch: `port/register-mmap-0050`
Parent experiment: `285bf00` (`experiment: measure native Windows resident expert LRU`)

## Question

Can a small exact-byte VRAM cache keep one high-router-mass expert per streaming
layer and improve native Windows decode without changing router selection, weights,
quantization, or output bytes?

The implementation is opt-in:

```text
DS4_CUDA_STREAMING_EXPERT_CACHE_N=<slots>
DS4_CUDA_MOE_CACHE_POLICY=layer-top1
```

For each layer, the selected expert with the highest sum of current router weights is
admitted when the layer's resident expert is absent. All other selected misses retain
the existing direct file-to-compact path. A resident hit is copied device-to-device
into the compact top-k buffer. The default remains cache disabled.

## Cap48 long-run failure

An earlier cap48 coding run completed four server requests before the parent command
timed out while the harness was finalizing. Server request durations were 50.792,
45.810, 173.397, and 178.192 seconds for 64 tokens. The periodic hot-tensor loading
messages rose from 2, 2 to 18, 18 per request. Because the client summary was not
written, this is diagnostic evidence only and is not used as an `n=3` verdict.

The log behavior is consistent with a VRAM working-set cliff. Cap48 permanently
allocates 324 MiB outside the existing fd-cache/stream-pool policy. Once the hot
attention, norm, router, and shared-expert ranges no longer fit, they are repeatedly
evicted and reloaded. The messages are rate-limited heartbeats, not one message per
load, but the simultaneous duration and cached-byte oscillation demonstrate churn.

Diagnostic artifact:

- `g7_runs/g7_layer_top1_cyber64_cap48_clean_n3_stderr.log`


The cache buys real hits, but too few to repay router-weight D2H, admission I/O,
cache-to-compact D2D, and lost VRAM capacity. Counter totals include the discarded
warmup plus the one measured repeat.

## PocketMoE comparison

PocketMoE commit `c9e0f86b1cab545a55bf51e5bf6514e7502ccc45` was reviewed as a
design reference. Its heterogeneous runtime uses pinned host memory, quantized expert
transfer, a hot expert cache, and layer-local/semantic prefetch. Its main GPU expert
cache is nevertheless a global admit-on-miss LRU followed by device-to-device copy
into a layer slab, the same policy class rejected by G9 on this 12 GiB GPU:

- Runtime LRU: <https://github.com/lvyufeng/PocketMoE/blob/c9e0f86b1cab545a55bf51e5bf6514e7502ccc45/src/models/deepseek_v4/runtime.py#L48-L103>
- Cache-to-layer copy: <https://github.com/lvyufeng/PocketMoE/blob/c9e0f86b1cab545a55bf51e5bf6514e7502ccc45/src/components/moe/gpu_prefill_backend.py#L327-L352>
- Pinned staging ring: <https://github.com/lvyufeng/PocketMoE/blob/c9e0f86b1cab545a55bf51e5bf6514e7502ccc45/cpp_engine/src/dsv4_engine.cpp#L1139-L1219>
- Overlap/prefetch path: <https://github.com/lvyufeng/PocketMoE/blob/c9e0f86b1cab545a55bf51e5bf6514e7502ccc45/cpp_engine/src/dsv4_engine.cpp#L8263-L8384>

PocketMoE's reported hardware and throughput are not directly comparable to the RTX
3060 measurements here. Its PolyForm Noncommercial license also means implementation
ideas should be independently recreated rather than copied:
<https://github.com/lvyufeng/PocketMoE/blob/c9e0f86b1cab545a55bf51e5bf6514e7502ccc45/LICENSE#L11-L20>.

## Verdict and next lever

`layer-top1` is rejected as a production default. It remains opt-in to preserve the
negative experiment and enable future controlled variants. There is no supported
speed claim from it.

The next transport experiment should target allocator churn rather than reserve more
VRAM: retry `cuda_stream_pool_take(aligned)` inside the allocation/eviction loop so a
reclaimed exact-size buffer is reused instead of synchronizing, freeing, and then
calling `cudaMalloc` again under WDDM. After that, test overlap of selected expert H2D
with already-independent shared-expert compute. File I/O queue depth remains 1 because
G8 measured QD2/QD4 regressions.
